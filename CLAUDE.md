# Waymark — context for Claude Code

Read this before changing anything. It carries over decisions made in an earlier

## What this is

A platform for college students to find their next career-growth opportunity on
campus — club events, speaker talks, info sessions, research openings,
fellowships, programs — across every department, not just their own. UCSD is the
first target school. Long-term vision: every university. "Canvas, but for
opportunities."

The core problem: these things are scattered across hundreds of siloed clubs,
departments and centers with no front door. Most students don't know the
resources exist.

The key feature is an AI recommendation engine: student's major, interests and
free-text career goals in, a ranked feed of opportunities out.

## The four bugs that killed the last build

This app was rebuilt from scratch because of these. All four are fixed here.

**1. There was no `src/middleware.ts`.** This was the "sign-in doesn't work" bug.
Supabase keeps the session in cookies that must be refreshed on every request by
Next.js middleware. Without it the browser holds a session the server can't see:
you sign in, get redirected to `/dashboard`, the server renders it, `getUser()`
returns null, and you bounce back to `/auth` — indistinguishable from a wrong
password.

`src/middleware.ts` and `src/lib/supabase/middleware.ts` are load-bearing. Do not
delete them, do not narrow the matcher so protected routes stop matching, and do
not replace the `getUser()` call with `getSession()` — that call *is* the
refresh, and `getSession()` trusts the cookie without revalidating it.

**2. Env var names drifted from what the code read.** Fixed by `npm run doctor`,
which validates names, formats and live credentials before you waste time
debugging. Run it first whenever anything is strange.

**3. Email confirmation was on during development.** Signup returns success with
no session; the free SMTP sender is rate-limited to a handful per hour. Reads as
broken auth. Keep **Confirm email OFF** in Supabase while developing. The
`/auth/callback` route already exists for when it's turned back on for real
students. `auth-form.tsx` handles both cases explicitly.

**4. Embeddings were computed on every dashboard render.** A missing HF token
silently degraded the feed to a date-sorted list while still looking fine, which
is how a demo gets recorded with the core feature switched off.

## Architecture rules

### Embeddings are computed at write time, never at read time

- **Opportunity vectors:** generated by the seed/ingest script, stored in
  `opportunities.embedding`.
- **Profile vector:** written only by `refreshProfileEmbedding()` in
  `src/lib/profile-embedding.ts`. Onboarding, profile edits and post-event
  reflections all route through it, so there is exactly one definition of what a
  student "means". It rebuilds from the stored row every time rather than
  patching the old vector.
- **The dashboard calls `match_for_me()`** — a Postgres function that reads the
  caller's stored embedding via `auth.uid()` and does a pure pgvector search. No
  embedding API call on the render path, no vector round-tripping to the browser.

If you ever find yourself calling `embed()` inside a page component, that's the
regression.

Two things that shape the profile text, both easy to undo by accident:

- **Only positively-rated experiences are folded in.** A vector cannot express
  "less like this", so including an event the student disliked pulls the feed
  toward exactly what they disliked. `buildProfileEmbeddingText()` filters to
  rating >= 2.
- **all-MiniLM-L6-v2 truncates at 256 word pieces and says nothing.** Order is
  load-bearing: stated goals first, free-text resume last and capped, because
  the resume is what we can most afford to lose off the end.

### Row Level Security is the whole security model

The publishable key is compiled into the browser bundle. Anyone can read it. RLS
is the only thing standing between that key and every student's data.

- Every table gets `enable row level security` **in the same migration that
  creates it**, plus explicit policies. Never later.
- `npm run doctor` calls `rls_status()` and fails the run if any table in
  `public` has RLS off.
- `createAdminClient()` (secret key) **bypasses RLS entirely**. Use it only in
  scripts and server-only route handlers, only for opportunity data, never with
  unvalidated user input. If an RLS error tempts you to reach for it, the policy
  is wrong — fix the policy.
- Never give a variable holding a secret a `NEXT_PUBLIC_` prefix. doctor checks
  for this explicitly because it's the one mistake that can't be quietly undone.

### Failures degrade, they don't cascade

Groq is a garnish. If the key is missing, expired or rate-limited, cards render
without the "why this matched" line — the feed never breaks. Justin's Groq key
is set to expire around **10 December 2026**; when explanations vanish, that's
the first thing to check.

2. Authentication → Sign In / Providers → Email → **Confirm email OFF**.
3. Site URL `http://localhost:3000`.
4. Free-tier projects **pause after ~7 days idle**. If doctor reports the
   database unreachable and the keys look right, that's almost always it.

  match functions, `rls_status()` diagnostic
- `scripts/doctor.ts`

**Phase 1 test gate — confirm this passes before building further:**

1. `npm run doctor` → all green
2. Sign up → land on `/onboarding` (404 until Phase 2 — that's expected, the
   redirect is what matters)
3. Navigate to `/dashboard`, **hard refresh** → still signed in
4. Sign out → back to `/`
5. Visit `/dashboard` signed out → redirected to `/auth`

If step 3 fails, the middleware is the cause. Nothing else.

**Done — Phase 2:** `/onboarding` (name, major, year, interest pills, free-text
career goals) writing the profile and its embedding, via `POST /api/onboarding`.
`/dashboard` redirects there when `onboarding_complete` is false — that redirect
is the only thing routing an existing account into onboarding, since the auth
form only sends new signups.

**Done — Phase 3:** `npm run seed` (56 opportunities + embeddings, 16 per HF
request), `/dashboard` ranked feed via `match_for_me()` with % match badges,
`/explore` full catalogue by date, `/profile` editing that recomputes the
embedding, org-type tabs, category filters and search, Groq explanations via
`POST /api/explain` fetched after paint.

Two things found while building it, both the silent kind:

- **`match_opportunities()` returned 40 rows no matter what `match_count` said.**
  That is pgvector's HNSW `ef_search` default, not a bug in the query. Fixed with
  `set hnsw.ef_search` on the function — applied, and verified returning all 56.
- **`formatMatch()` was calibrated before there was data** and rendered the best
  match as "29%". Rebased on the observed 0.20–0.50 band; re-check it if the
  catalogue or profile prompt changes shape.

**Done — saved, calendar and the reflection loop:**

- `/saved` — favourites, split into pending-review, upcoming and attended.
- `/calendar` — month grid of saved events. Opens on the month holding the next
  saved event, not today, so it is never an empty grid.
- `profiles.resume` — optional free text. Deliberately not a file upload: it
  feeds the embedding directly, and a bucket would add an RLS surface and a
  parser for one field.
- **The reflection loop.** A saved event whose `starts_at` has passed and whose
  `attended` is still null prompts "did you go?" → how useful (1–3) → optional
  takeaway. Answering yes recomputes the profile embedding, so what a student
  actually attended and valued starts pulling the feed. Verified: one
  attended robotics event moved every robotics event up the ranking, the largest
  by 31 places.
- Recurring and undated opportunities never prompt — asking "did you go?" about
  standing office hours is noise.

**A typing trap, verified against the live API:** supabase-js infers an embedded
join (`select("*, opportunities(*)")`) as an **array**, but `opportunity_id` is a
plain many-to-one FK, so PostgREST returns a single **object**. The casts in
`src/lib/saved.ts` and `src/lib/profile-embedding.ts` are correct; "fixing" them
into array access renders every saved and calendar page blank.

## Design

The brand kit lives in `../brand` (one level up from this repo, not inside it).
Ink is `#141A2E`; that plus white is the whole palette, with a trail-blaze amber
accent defined as `--accent`. The accent is for emphasis and match scores only —
it fails contrast as body text on light backgrounds.

`../meridian` is a **different person's** project (a former teammate's, in an
overlapping space). It was used as a reference for Supabase auth wiring and
general Next.js conventions, which are standard patterns. Do not copy its
landing page, copy, or visual identity into this repo.

## Conventions

- Server Components by default; `"use client"` only where there's state or an
  event handler.
- Comments explain *why*, especially where something looks odd — a workaround,
  a security constraint, a bug being prevented. Don't narrate what the code
  already says.
- Any table added needs RLS plus policies in the same change.
- Don't add dependencies for things a few lines of code would do. This has to
  stay maintainable by one person who's still learning the stack.
